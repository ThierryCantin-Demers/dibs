Working system, written up for porting

Remote Benchmark Lock

Several coding agents share one fast machine. Benchmarks cannot overlap with anything, including each other, so access has to be serialized. This is a single bash script that wraps ssh in a shared/exclusive lock, plus the findings that took it from working to trustworthy. Everything here is portable; the parts that are not are listed explicitly.

01The problem it solves

One person, several agents, one machine worth measuring on.

The laptop is an Intel CPU and integrated GPU sharing one pool of memory, so its benchmark numbers and kernel timings are noise. The real machine sits on the network. Several agents work at once across different repositories, and more than one of them needs that machine at any given moment.

Benchmarks cannot run in parallel without defeating the point. Worse, a compile running beside a benchmark contaminates it as surely as a second benchmark would, so an exclusive job has to exclude ordinary work too, not just other exclusive jobs.

Before this existed, coordination was manual: telling each agent, by hand, that another one was using the machine right now. That does not scale past about two agents and it fails silently, because an agent that was not told simply runs its benchmark on top of someone else's and reports a number that looks fine.

Copies are work too

An rsync of a large tree is seconds of writeback and memory bandwidth landing on top of whatever is being measured, so it belongs under the lock as much as a build does. The difficulty is that rsync runs on the client, so there is no remote command to put the lock around. The way through is rsync's own -e: point it at the wrapper, which then holds the lock while passing rsync's protocol stream through as its workload. One transfer, one holder, visible in the queue like anything else, and it costs a single mode rather than a reimplementation of file copying.

The shape of the fix

Replace ssh box <command> with box <command>. Same ergonomics, but the command runs under a lock held on the target machine. Agents need to learn exactly one thing: which of two modes their command is.

The display is coloured when the far end is a terminal: red or amber for the machine's state, green for idle, and a hue derived from each agent's own name so one session reads as one thing wherever it appears. Piped output and the test suite see plain text, and NO_COLOR is honoured.

Modifiers: --wait <s> to give up rather than queue past a bound, --max <s> to bound how long the job may hold the lock, --label <name> for what shows up in the queue.

Two of these matter more than they look. An agent that cannot tell "the machine is down" from "my command failed" will retry a broken thing forever, and an agent that cannot tell "queued" from "hung" will kill its own work.

03Shape of the thing

One file, two halves, no daemon, nothing installed on the target.

The script contains a second script as a here-document. The local half parses arguments, decides who the caller is, and opens the connection. The remote half does the locking, runs the workload, and reports. It is shipped on every call: base64 on the command line, decoded into a temporary file on the target, executed, and unlinked by its own exit trap.

{{SNIP_SHIP}}

Shipping the remote half per call is worth a moment. The alternative is installing something on the target and keeping it upgraded, which introduces a version skew between the two ends that nobody will notice until it produces a wrong answer. This way the two halves cannot disagree, and a machine with an ssh daemon and bash is already fully provisioned.

The lock is the job's own process

There is no lock file to clean up and no stale-lock timeout to tune. The lock is an open file descriptor held by the process running the workload, so it is released by the kernel when that process dies, however it dies, including SIGKILL and a power loss on the client. The records in the lock directory are decoration for the status display; the kernel holds the truth. Everything in the status display is written to be reconciled against a live pid, and a record whose pid is dead is pruned on sight.

04The lock protocol

Two files, both in a per-user directory on tmpfs, and two descriptors.

{{SNIP_GATE}}

Everyone passes through the gate exclusively, then takes the real lock shared or exclusive, then releases the gate. The consequence is the whole point: an exclusive waiter keeps holding the gate while it waits for the real lock, so every later arrival blocks at the gate behind it. Without that, a steady trickle of one-minute builds means an exclusive waiter never sees a free moment and starves indefinitely.

The non-blocking probe before the real acquisition exists only so the caller learns it is about to wait. A job that goes quiet for twenty minutes gets killed by its own caller's timeout and leaves the work undone with nothing to explain why; a job that says "queued, and here is what is ahead of you" can be dealt with. The probe is safe because the gate is still held while it runs, so nothing can take the lock between the probe and the real acquisition.

One bounded exception, measured before it was written

Strict priority makes every shared job wait out the whole benchmark ahead of it, and on this machine three quarters of shared jobs finish in under five seconds while a benchmark runs for up to twenty minutes. That is a 250x amplification applied to the overwhelming majority of the traffic.

So a shared job may skip the gate, on two conditions that must both hold: the benchmark has been waiting less than DIBS_PATIENCE (60s), and this job's own recorded median is under DIBS_QUICK (10s). Its own, not its mode's, because the median across all shared jobs here is under a second and would wave the four minute ones through as readily as the instant ones. No history of its own means no exception. A benchmark can therefore be delayed by the sum of the two, about seventy seconds, and no more.

One thing this depends on that is easy to get wrong: the median is filed under the job's label, so it only exists if that label has been timed before. Labels naming the particular run rather than the kind of work file a duration nothing will ever look up, and two thirds of the labels on this machine ended up that way. The estimate falls back from the label to that agent's other jobs and then to the mode, but the exception above deliberately requires the label's own history, since what an agent usually takes is not what this job takes.

Note what cannot go wrong. This decides who waits and nothing else: once a benchmark holds the lock, flock refuses every shared caller regardless of what the policy returns. A bug in it can starve a benchmark. It cannot contaminate one.

Two knobs worth knowing are the wrong ones. Time since the current shared work started is not it, since that measures the wrong clock: the harm belongs to the benchmark, so it should be counted from when the benchmark began waiting. A count of admitted jobs is not it either, because they run concurrently with the work already in progress, so the delay is set by the single longest one let through, not by how many.

Arrival order is reported, not promised

The queue display sorts by arrival because that is what a queue looks like to a person. The kernel picks the actual wake order among waiters on the same lock, and the display says so rather than implying a guarantee it cannot keep.

05Findings

Each of these was a bug that reached production, most of them found by the machine misbehaving rather than by reasoning. They are the reason the script is 776 lines instead of 80.

A job has to die with the caller that started it

Symptom when missingYou kill the agent, and the benchmark keeps running on the target holding the lock until it finishes on its own.

Three mechanisms, because each covers a different failure:

  • The local ssh client must die with its parent. An ssh client whose parent dies otherwise keeps running as an orphan with the channel up. setpriv --pdeathsig=TERM has the kernel signal it the moment the parent dies, SIGKILL included, which no userspace cleanup can cover.
  • The remote half learns through EOF on its stdin. A closed channel does not become a SIGHUP under every ssh server, so waiting for a hangup is not portable.
  • Our end must never reach EOF on its own. Stdin for the ssh client is a fifo held open read-write, which delivers neither data nor EOF while we live and closes with us when we do not. If the fifo cannot be created, the watch is disabled with a warning rather than falling back to whatever stdin we were handed. A job outliving its caller is a nuisance; a job killed while its caller waits for it is the failure this exists to prevent.

The trap that cost the most time: bash redirects a background job's stdin from /dev/null in a non-interactive shell. The watcher is a background job, so it read EOF instantly and killed the very job it was protecting, on every single run. The channel has to be handed to it on another descriptor.

{{SNIP_WATCH}}

The watcher also starts before queueing, not after acquiring. A caller can die while its job is still in the queue, and that job should leave the queue rather than hold a place for twenty minutes and then die the instant it is let in.

Never allocate a TTY

Symptom when missingJobs wedge forever holding the lock. The machine looks busy with something that is doing nothing at all.

ssh -tt gives the remote a TTY, and with one, every tool downstream believes it is interactive. A git diff --stat in a build script opened its pager and blocked on a keystroke nobody would ever type. Two jobs wedged the machine this way before the cause was found, and from the outside it looked like a lock bug.

No -tt. Redirect the workload's stdin from /dev/null, and set the environment that tells tools nobody is watching:

The workload must not inherit the lock descriptors

Symptom when missing--status reports the machine idle while every new job queues forever behind nothing.

The lock is an open file descriptor, so anything that inherits it holds the lock. If the workload spawns a child that outlives its parent, that child keeps the lock with no holder record to show for it, and the status display swears the machine is free. Close the descriptors when launching the workload:

{{SNIP_FDS}}

Belt and braces on the display side too: when there are no holder records, try the lock non-blockingly. If that fails, the lock is held by an orphan, and the display says so along with how to find it (fuser -v on the lock file).

A holder's clock starts when it acquires, not when it arrived

Symptom when missingA job that queued for 13 minutes and has been running for 3 reports 16m23s, and every number computed from that elapsed is wrong in the same direction.

The queue record was promoted to a holder record with mv, which is atomic and convenient and keeps the arrival timestamp. Three separate things then measured a stretch the job had spent waiting: the remaining-time estimate subtracted a queue wait from a run-length median, the overrun check compared against mostly-queue time, and the idle check asked whether the job had burned CPU during minutes it had spent queued. Rewrite the record on acquisition instead of renaming it.

The general lesson is worth keeping: when one field feeds several derived numbers, an error in it does not look like one bug, it looks like the feature being unreliable.

CPU accounting has to count children that were already reaped

Symptom when missingA healthy twelve-minute sweep is reported as idle and the user is told to kill it.

A supervisor that spawns a benchmark, waits for it, and spawns the next owns almost no CPU itself at any instant, and ps TIME reports only living processes. The work lives in cutime and cstime, which the kernel credits to a parent when it reaps a child. Sum all four fields across the holder and every descendant:

{{SNIP_CPU}}

Descend through /proc/<pid>/task/<tid>/children rather than rebuilding the tree from every process's parent. It touches the holder's own subtree instead of all 598 processes on the machine, and every step is a shell builtin. Keep the parent-scan version as a fallback for kernels without CONFIG_PROC_CHILDREN, and test the two against each other, or the fallback will rot unnoticed.

Idle is a rate, not a total

Symptom when missingThe signal can only ever catch a job that wedged before it started, which is not the case that blocks the machine.

A cumulative count answers whether a job has ever done anything. The sweep that runs fine for an hour and then hangs carries plenty of CPU behind it forever, so it is never flagged. Each look writes what the holder's tree had burned into a small file next to the holder record, and the next look flags the job if that number has not moved.

It says nothing at all from a single sample, because one reading genuinely cannot distinguish a job that is working from one that stopped before anyone looked. That makes a --watch left running useful for more than watching: it supplies the samples.

A successful read can return non-zero

Symptom when missingThe CPU walk silently reports zero for every job, and the idle detector calls a busy machine idle.

If the status display is polled, it has to be fork-free

Symptom when missingWatching the queue costs the benchmark more than it tells you, which makes the tool self-defeating.

The original redraw forked about thirty times and scanned every process on the machine to find the holder's descendants: 31ms of CPU per look. Four changes took it to 2.2ms and zero forks.

  • Walk the holder's subtree through the kernel's child lists instead of scanning all of /proc. Cost now scales with the job's process tree, not the machine.
  • Format with printf -v var rather than $(func). Command substitution forks a copy of the shell, and a status line contains several.
  • Insertion-sort the queue in the shell rather than calling sort. The queue is a handful of entries; the fork costs more than the sort.
  • Cache the per-label medians between redraws. They can only change when a job finishes, and a job cannot finish without leaving the lock directory, so the set of records in that directory is a free and exact invalidation signal.

The last one generalizes: if you need to know whether a derived value is stale, look for something you are already reading that changes exactly when it does.

Fail fast, and diagnose

Symptom when missingAn agent hangs on a connection attempt, then reports a failure whose cause is invisible, then tries again.

A short ConnectTimeout, BatchMode=yes so it can never sit at a password prompt, and on failure an actual diagnosis rather than ssh's exit code. In this setup the machine is reached over a VPN that needs a login after a reboot, so the failure path distinguishes "VPN logged out", "VPN up but the machine is not on the network", and "machine is up, so this is an ssh problem", then tells the caller in as many words not to retry in a loop.

This part is the most environment-specific thing in the script and the easiest to replace. What matters is the shape: one exit code that means "not my command's fault", and a message that names the next action.

A signal has to compare a job against itself

Symptom when missingA perfectly healthy five minute sweep is accused of running three times longer than it should.

Remaining-time estimates come from a median of that label's own past runs, and fall back to the median across the whole mode when a label is new. The fallback is a reasonable thing to show, as a rough idea of what benchmarks on this machine cost. It is not a statement about the job in front of you, and the overrun check was treating it as one: a long sweep with no history of its own was measured against a median dominated by unrelated one minute benchmarks, and duly declared stuck.

Guard the accusation on where the number came from. A signal that is confidently wrong is worse than no signal, because it teaches people to stop reading the display, and it takes the true warnings down with it.

kill -0 answers a different question than the one being asked

Symptom when missingOn a machine with more than one account, live jobs vanish from the queue display and the machine looks emptier than it is.

Records are reconciled against a live pid, and the obvious test for "is this process alive" is kill -0. It returns EPERM for a process owned by another user, which bash reports as failure, so the record for a colleague's running benchmark is pruned as though the job had died. This one never fires with a single account, which is what makes it worth knowing before porting rather than after.

Recognize yourself

Symptom when missingAn agent working directly on the fast machine bypasses the lock entirely, which is exactly when it matters most.

The same script is installed on the client and on the target. It compares hostname -s against the target's name and, when they match, runs the remote half locally through a pipe instead of trying to ssh to itself. One binary, one set of rules, and the lock covers work started on the machine itself.

Note the one asymmetry: in local mode there is no channel, and stdin belongs to whoever called. The caller-death watch has to be switched off there, or redirecting from /dev/null kills the job immediately. Ordinary process death covers that case anyway, since the caller and the job share a machine.

06Knowing whose job it is

The queue is only half useful if you cannot tell which agent put something in it.

With several agents running, a command in the queue gives no way back to the session that started it, so the only way to ask about a job is to guess which window it came from. Each caller stamps its own record with a name resolved on the calling machine, which is the only machine that knows it. The target just stores the string.

{{SNIP_STATUS}}

In this setup the name is the title of the Claude Code session, read from the desktop app's own metadata using the session id in the environment. That is the least portable piece of the whole script and the fallbacks matter more than the happy path.

{{SNIP_AGENT}}

Adapt in order of preference: a session or window identifier from the environment; a tmux or terminal window name; the working directory; or an explicit --agent flag that the agent rules tell agents to pass. Any of them beats an opaque pid. Whatever is chosen, the same string should also go into the log, so the question "what has that agent been running all afternoon" has an answer.

The one that will bite: several user accounts on the target

The lock directory is per-user, under /run/user/$(id -u). If everyone logs into the target as the same account, that is correct and nothing needs doing. If two people log in as different accounts, they will each get their own lock and will not see each other at all, which is worse than having no lock, because the status display will confidently report an idle machine.

For a shared box, move the lock directory somewhere both accounts can reach, for example a setgid group-writable /run/lock/<name> created by a tmpfiles.d rule, and make sure the records are group-readable. The kill path needs a thought too: signalling another user's process requires either the same group and a cooperating job, or sudo.

Platform requirements

  • Linux on both ends. The CPU accounting reads /proc. Fedora client and Ubuntu target are both fine.
  • util-linux for flock and setpriv. Present by default on both. Without setpriv the script drops to a softer caller-death guarantee rather than failing.
  • GNU coreutils for timeout --kill-after.
  • bash 4.2 or newer for printf -v. Bash 5 is used for EPOCHSECONDS where available, with a fallback to date.
  • An ssh daemon and bash on the target. That is the entire install requirement.
  • macOS as a target would be real work: no /proc, no flock or setpriv in the base system. The lock protocol would survive; the process accounting would need rewriting against libproc.

08Making agents actually use it

A wrapper nobody calls is worse than no wrapper, because the status display becomes a lie.

Two pieces. First, the rules file the agents read, which has to explain the shared/exclusive distinction in terms of what agents actually do, and has to tell them how to call it. The most important line turned out to be about backgrounding: a queued job can wait twenty minutes, which is longer than a foreground tool call survives, so an agent that runs it in the foreground loses the work and reports a failure whose cause is invisible.

{{SNIP_RULES}}

A front end is optional and comes free of the wrapper: --watch --json is a line-delimited feed over the same single connection, so a dashboard reads structured state instead of parsing a display meant for a person. The one built here is a ratatui terminal view that renders the feed and shells back out to the wrapper for actions, which means it cannot drift from what the wrapper would have said and needs no privileges of its own.

Second, a hook that blocks direct ssh to the machine and explains what to use instead. This matters more than it sounds: agents that already know ssh box ... will keep using it, and one unlocked command ruins whoever is benchmarking. The hook is Claude Code specific (PreToolUse on Bash, exit 2 to block and feed stderr back to the agent), and it strips here-document bodies before matching so that writing about ssh in a file does not trip it.

Note that hooks apply to sessions that are already running, while a rules file is read at session start. Adding the hook fixed behaviour immediately across every open agent, which is a useful property when rolling this out to a team mid-week.

09Testing, and two traps in it

Two suites, split by whether they need the real machine.

  • Local suite, {{LINES_TEST}} lines, 58 assertions, about 15 seconds. Never leaves the client. Every case runs against a scratch lock directory with the script forced into local mode, so it is safe to run while other people's jobs are on the real machine.
  • Live suite, {{LINES_LIVE}} lines, 14 assertions, about 6 seconds. Needs a real channel, because "the job dies with its caller" cannot be shown without one. It refuses to run unless the machine is idle and the operator passed --machine-is-mine, since it takes the exclusive lock and kills things.

Trap one: a fixture sized in iterations is only a fixture on the machine it was written on

The idle detector's test spawned children that ran sum(range(9000000)) and expected them to clear a two-second CPU threshold. On the machine where it was written that took 77 milliseconds. The test passed anyway for weeks, on an unrelated age guard, so it was pinning nothing at all. Size fixtures in wall time:

{{SNIP_FIXTURE}}

Trap two: a poll loop's time budget is the cost of the thing it polls

A test waited for a condition by calling --status up to sixty times, which took about three seconds because --status was slow. Making --status fifteen times faster made that loop finish in under a second, and the test started failing for a reason that had nothing to do with what it was testing. Wait on an event, not on a spin. A fifo costs no CPU and releases exactly when told:

{{SNIP_SYNC}}

The same applies to fixtures that need to hold the lock: block them on a fifo rather than a sleep or a spin. The suite went from over 300 seconds of busy-waiting to 15 seconds by changing nothing but how it waits.

What is worth pinning

Every finding in section 05 is a test. That is not a coincidence: each of them was a silent failure, and the only defence against a silent failure coming back is an assertion that fails loudly. The two walks of the process tree are checked against each other, the idle detector is checked in both directions, and the caller-death behaviour is checked over a real connection.

10Still open

  • Environment knobs do not cross ssh. The tuning variables only take effect in local mode, since ssh does not forward the environment. On the target the defaults apply and changing them means editing the script. Sending them explicitly through the command line would be a small change if it matters.
  • Hard-killed jobs leave a few KB behind. The temporary remote script deletes itself from an exit trap, which cannot run under SIGKILL. Not worth cleanup code unless it accumulates.
  • One resource, one lock. A machine with several GPUs where independent benchmarks could run per device would want a lock per device. The protocol generalizes directly, the display does not.
  • No fairness beyond writer priority. Among waiters of the same kind, the kernel decides. In practice this has never mattered; with many agents it might.
